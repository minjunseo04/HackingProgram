# BoundaryCheck 사용성 테스트 안내서

**목적:** 설치형 앱의 기본 흐름에서 사용자가 막히는 지점을 찾는다. 이 테스트는 실제 앱 제작자의 수요, 취약점 탐지 정확도, 구매 의사를 검증하지 않는다.

**상태:** 안내서와 기록 양식만 준비됨. 사용자가 명시적으로 요청하기 전까지 참가자를 모집하거나 실제 테스트·피드백 수집을 진행하지 않는다. 제품 기능이 완성되더라도 자동으로 시작하지 않는다.

## 테스트 전에

1. 사용자가 사용성 테스트를 명시적으로 요청한 뒤에만 진행한다. 진행할 때는 앱을 v0.6.6 이상으로 업데이트하고 사이드바 아래 버전을 확인한다. 업데이트 확인이 실패하면 [GitHub Releases](https://github.com/minjunseo04/HackingProgram/releases/latest)에서 ZIP을 다시 받아 새 폴더에 압축을 풀어 실행한다.
2. 참가자에게 “앱 사용 중 막히는 지점을 찾는 테스트이며, 원하면 언제든 중단할 수 있다”고 설명한다. 동의한 경우에만 익명 메모를 남긴다. 이름·연락처·화면 녹화는 수집하지 않는다.
3. 참가자에게 먼저 기능을 설명하거나 화면을 안내하지 않는다. 참가자가 요청해 도와준 경우 어느 단계에서 무엇을 알려줬는지 기록한다.
4. 프로젝트 데이터와 인증 비밀이 들어 있는 파일은 사용하지 않는다. 저장소의 합성 자료 [`sample.har`](../poc/sample.har) 또는 [`sample-openapi.json`](../poc/sample-openapi.json) 중 하나만 가져온다. 두 자료에는 가짜 값만 있다.

## 참가자에게 줄 과제

권장 시간은 20~30분이다. 아래 과제를 하나씩 보여주고, 참가자가 생각을 말하며 직접 수행하도록 한다.

### 과제 1 — 첫 화면 이해

“이 프로그램이 무엇을 관리하는지 살펴보고, 프로젝트 자료가 어디에 저장되는지와 업데이트 확인 때 무엇이 전송될 수 있는지 찾아 말해 주세요.”

관찰할 점: 저장 범위와 업데이트 연결 안내를 찾는 데 걸린 시간, 문구를 잘못 이해한 부분.

### 과제 2 — 요청 자료 가져오기

“준비된 합성 HAR 또는 OpenAPI 파일을 가져오고, 어떤 요청이 목록에 들어왔는지 확인해 주세요. 가져온 뒤 실제 요청이 전송됐는지도 확인해 주세요.”

관찰할 점: 파일 선택, 가져오기 결과 해석, 요청이 실행되지 않는다는 점의 이해 여부. 가져오기는 요청 초안을 만드는 동작이며 대상 서버로 요청을 보내지 않는다.

### 과제 3 — 신원과 기대 접근값 설정

“Acme 조직의 owner와 Birch 조직의 member라는 가상 테스트 신원 두 개를 만들고, 요청에 연결한 뒤 한 신원은 허용, 다른 신원은 거부로 설정해 주세요.”

관찰할 점: 신원 추가·저장 위치, 요청과 신원 연결, 허용/거부 설정의 의미를 이해하는 데 막힌 부분. 계정 비밀번호나 토큰은 입력하지 않는다.

### 과제 4 — 내장 로컬 예제 결과 읽기

“내장 로컬 예제에서 안전 예제와 취약 예제를 차례로 실행하고, 어떤 결과를 검토해야 하는지와 그 이유를 설명해 주세요.”

관찰할 점: 예제 실행 위치, 안전/취약 결과 구분, 결과의 근거와 한계를 읽는 방법. 내장 예제는 앱이 만든 가상 계정·문서만 사용하며 `127.0.0.1`의 임시 포트로 실행한다. 저장한 프로젝트 주소나 가져온 요청은 사용하지 않는다.

### 과제 5 — 보고서 저장과 다시 열기

“예제 결과를 임시 위치에 보고서로 저장하고, 저장한 보고서를 다시 열어 어떤 내용이 기록됐는지 확인해 주세요.”

관찰할 점: 저장 버튼과 파일 위치, 보고서 재열기, 보고서에 응답 본문이나 프로젝트 자료가 포함된다고 오해하는지 여부.

## 테스트 범위와 안전

- 실제 웹사이트, 고객 앱, 학교 시스템, 인터넷 호스트에 연결하지 않는다.
- 합성 HAR/OpenAPI만 가져온다. 다른 HAR에는 쿠키·토큰·개인정보가 들어 있을 수 있으므로 사용하지 않는다.
- 가져온 요청은 초안일 뿐 실행하지 않는다. 실행 과제는 앱의 내장 로컬 예제만 사용한다.
- 제한된 쓰기 예제는 기본 사용성 테스트에 포함하지 않는다. 사용자가 별도로 확인할 때만, 앱 설정·실행별 동의·최종 확인을 모두 통과한 내장 로컬 fixture에서 진행한다.
- 결과는 해당 가상 fixture의 동작만 보여준다. 실제 서비스의 안전성이나 제품의 시장성을 입증하지 않는다.

## 관찰 기록 양식

참가자 식별자는 `P1`, `P2`처럼 임의 코드만 쓴다. 한 참가자마다 과제별로 기록한다.

| 참가자 | 과제 | 완료/막힘 | 걸린 시간 | 도움 제공 | 처음 막힌 지점·혼란 | 심각도 | 제안 또는 익명 메모 |
|---|---|---|---|---|---|---|---|
| P1 | 1 |  |  |  |  |  |  |
| P1 | 2 |  |  |  |  |  |  |
| P1 | 3 |  |  |  |  |  |  |
| P1 | 4 |  |  |  |  |  |  |
| P1 | 5 |  |  |  |  |  |  |

심각도는 다음 기준으로 통일한다.

- **막힘:** 도움 없이 다음 단계로 갈 수 없거나 기능을 잘못 이해해 테스트를 계속할 수 없음.
- **큼:** 도움을 받아 완료했지만 결과나 안전 범위를 잘못 이해할 가능성이 큼.
- **작음:** 완료는 가능하고 의미도 이해했지만 문구·배치가 헷갈리거나 느림.

## 결과 정리

테스트 후 다음 항목만 요약한다.

- 참가자 수와 실제 테스트한 앱 버전
- 과제별 막힘 횟수와 반복된 혼란
- 참가자 도움 없이 완료된 과제와 도움을 제공한 과제
- 우선 수정할 문제 1~3개
- 테스트하지 않았거나 판단할 수 없었던 항목

사용성 결과는 UI 개선에만 사용한다. 실제 앱 제작자 인터뷰, 반복 사용, 유료 파일럿이 따로 없으면 시장성이나 결제 의사가 확인됐다고 기록하지 않는다.
